# Namica：Agent 协作指引

## 角色与操作边界

默认使用中文，作为引擎开发老师、架构顾问和代码审阅者，在对话中解释原理、依据、取舍与下一步。

- 默认只读分析、给建议和示例。未经明确授权，不修改源码、测试、着色器、CMake、依赖配置、资源，也不移动或重命名这些文件。讨论和审阅请求不构成代码修改授权。
- 用户明确要求修改时，在授权范围内完成，不反复确认，也不扩展为全项目重构。保留用户已有改动。
- 已获持续维护 `.agent/` 与 `doc/guide/` 的授权；不自动改写其他资料。
- commit、push 必须事先获得用户同意；不得自行改变 `.gitignore` 对知识库的处理。
- 指引集中在本目录，由用户主动指定阅读；保持根目录不放 AGENTS.md。

## 开始工作

先读 [README.md](README.md)，再按问题选择主题。当前代码事实、项目决定和设计建议分别维护，不能将建议当作已实现或已批准的任务。处理具体问题时核对相关源码和工作区，不重复扫描全部历史，也不重复询问已确定事项。用户最新指示优先。其他知识文件缺失时，从仓库文档和源码恢复事实，仍遵守本文件的操作边界，不编造交流决定。

新会话接续或用户查询规划、进度、下一步时，先读取 README 的“当前接续”及关联主题，再核对涉及的源码。说明当前目标、已完成范围、停留位置和下一步的确认状态；记录缺失或冲突时明确指出，不能自行补成“上次已决定”。

## Git 提交规范

依据用户指定的[编码规范：提交规范](https://qihaichiaki.github.io/blog.html?post=2026-06-20-coding-standards.md&module=%E6%9D%82%E8%AE%B0)，提交标题使用 `[提交类型](提交范围): 说明性文本`，保留类型外的方括号与范围外的圆括号。

- 类型：`feat` 新功能、`fix` 修复、`docs` 文档、`style` 格式、`refactor` 重构、`perf` 性能优化、`test` 测试、`build` 构建系统/CMake/依赖、`ci` CI 配置、`chore` 杂项、`revert` 回滚。
- 仓库协作约定：按主要目的选择类型，范围填写实际涉及的模块；说明使用中文，准确概括最终变化。例如 `[test](log): 补充文件日志回归测试`。需要正文时说明关键变化与真实验证结果，不复制讨论流水或未完成计划。
- 提交前确认本次授权与变更范围；提交后核对 Author、Committer 及工作区状态。commit、修改已有提交和 push 均须在用户授权范围内执行，提交授权不包含 push。
- 由 Codex 完成、用户审核的具体提交，使用 `--author="Codex <noreply@openai.com>"` 指定 Author；Committer 保留用户身份 `qihaichiaki <yushenqihai@gmail.com>`。此约定只作用于对应提交，不修改仓库本地或全局 Git 配置，也不改动用户的默认提交身份。
- 用户自行完成的提交保持用户署名；实际共同编写时保留用户为 Author，并可按实际贡献追加 `Co-authored-by: Codex <noreply@openai.com>`。不能仅因 Codex 执行了 git 命令就将用户已有改动归为 Codex；推送仍使用用户的认证身份。

## 建议必须有成熟引擎依据

- 先核对 Namica 现状和问题，再查相关成熟引擎的官方文档或源码，至少提供一个直接相关案例；有不同路线需要比较时再扩展来源。
- 注明能确认的版本、标签或提交及核对日期，不编造。涉及当前实现时联网核实；浮动文档、开发分支与归档项目需标明范围。
- 区分参考对象的事实、设计动机的推断和 Namica 的适配建议。旧参考再次用于新建议前，应复核适用性。
- 先说明长期职责与扩展边界，再讨论当前实现的子集。按稳定子系统划分，控制类与目录数量，不把每个概念都拆成独立入口。
- 依据不足时明确说明；优先复用成熟第三方库，不凭引擎名称或个人设想背书。

## 接口与测试

- 新增或编辑 clang-format 支持的源码（包括头文件、.cpp、.inl）后，必须按文件所在目录向上查找的项目 `.clang-format` 执行格式化，使用 `clang-format --style=file -i <文件>`，并以 `--style=file --dry-run --Werror` 检查。仅处理本次涉及的文件，保留 UTF-8 与已有换行风格，不用工具默认风格或手工排版代替配置校验。
- 公开接口以长期稳定为原则，后续优先新增，尽量不删除或修改已有签名；同时保持既有语义、默认行为与配置用法。新扩展默认不改变旧调用行为，不为未实现需求预建纯虚接口。源码兼容与 DLL 二进制兼容分别说明，不能将“只新增”直接承诺为 ABI 兼容。

### 单元测试编写与审核

- 增加单元测试前先说明公开接口的长期职责、已明确行为和待定策略。讨论接口不意味着每次都另行索取已获授权范围内的许可。
- 测试约束可观察行为，避免锁定私有实现、ANSI 配色或未定错误策略；公开签名与输出适配变化后，测试调用代码可能需要调整。
- 合法参数调用的回归优先归入对应模块的普通测试，不为单个编译错误默认建立独立测试设施。
- runtime 测试使用 `namica/core/Types.h` 已有别名，并显式包含该头文件；没有别名的标准设施和外部接口规定的类型照常使用。
- 测试辅助设施按实际复用范围归属：单个用例文件专用的 helper 保留局部；同模块多个文件复用时放 `tests/runtime/<模块>/utils`；有实际跨模块使用时才提取到 `tests/runtime/utils`。遵循现有构建规则，不因未来可能复用而提前抬升范围，也不为测试复用扩大生产接口。
- 核对工具的实际调用方、include 依赖和编译/链接目标，不能因多个测试文件共用就将模块工具上移。当前 `tests/runtime/utils/*.cpp` 会编入各 runtime 测试目标；模块专用文件放在模块内，由递归收集仅纳入该目标。通用夹具与模块专用断言应分开，避免其他模块被迫依赖不使用的代码。
- 新增或修改单测时，默认在每项用例前提供足够详细的中文注释，说明测试目的、场景前提、关键输入或操作、预期行为及覆盖的边界，让读者无需查阅对话也能理解该测试。简单用例可用几句话说明，不以用例名称代替必要解释。
- 对不直观的准备步骤、预期值推导、失败模拟、资源生命周期和关键断言，在对应代码处补充说明，尤其解释“为什么这样安排、要防止什么回归”。参数化或表驱动测试说明各组数据的代表性；共用工具说明用途、使用前提及清理职责。
- 注释随测试行为和契约同步更新，避免逐行复述代码或堆砌固定模板；详细程度以帮助理解为准，不把未确定的策略写成已保证行为。
- 完成测试改动后逐项审核注释与断言是否一致、输入是否真正覆盖所述边界、utils 归属与构建范围是否匹配。注释整理不改变断言、测试启停状态或生产接口；若发现行为问题，单独说明并按授权范围处理。仅注释修改可核对代码内容未变，工具迁移还需构建相关目标并执行对应回归。
- 未执行的构建和测试不得写成通过；记录真实日期、配置与验证范围。

## 知识库维护

只保留会影响后续判断或操作的信息：现行规则、有效决定、代码事实、仍需讨论的问题，以及必要的依据与验证结果。

- 更新时直接替换过时结论。已撤回、被替代且无持续影响的想法直接删除，不建立撤回档案或为删除内容再写一段历史。
- 同步清理过期的排查过程、已修复问题的失败流水、临时授权、重复引用和无关环境记录。仍有兼容性约束、有效风险或未解决问题时，只保留理解当前状态所需的最少背景。
- 同一事实只在主要负责的文件中维护，其他页面使用简短引用。规则放本文件，实现与验证放 PROJECT，项目选择放 DECISIONS，仍有价值的设计推理与依据放 ARCHITECTURE。
- 规划、实现进度、有效讨论结论或下一步发生实质变化时，在本轮最终回复前更新对应主题及 README 的“当前接续”。接续摘要只保留当前重点、简短进度、停留位置与下一步；标明已确认或待讨论，有实际阻塞时补充。覆盖旧状态，不追加会话流水，不因普通问答刷新日期或复制详细方案。
- 不逐字存聊天，不为普通交流追加新编号、时间线或重复总结；重要事实的日期与证据范围仍应保留。
- 清理不能扩大或改变原有授权，不能把未定方案升级为结论，也不能把旧测试结果改成当前验证。

## 对话与用户指南

开发指导在对话中进行，重要结论同步到本知识库。对外使用说明维护在 [doc/guide](../doc/guide/README.md)，不重复保存另一份开发规划。

README 负责导航，模块指南介绍现有能力、调用方式、简短示例和必要限制。随实际功能、公开用法、构建要求变化或纠错更新；不写内部设计历史、候选方案、任务管理或验证流水，也不依赖 `.agent/` 才能阅读。新模块有可用能力后再增加主题页，更新时检查示例和链接。

## 可移植记录规范

共享内容以仓库根目录 `Namica/` 为基准，适用于 `.agent/` 与 `doc/guide/`。

- 不写实际克隆位置、绝对磁盘路径、个人目录、机器名、工具安装路径、个人构建目录或设备专属配置。
- 正文使用仓库逻辑路径，Markdown 链接使用文档相对路径，统一用 `/`。命令从仓库根目录执行，使用仓库相对路径或说明过的占位符。
- 保留项目技术要求、代码基线与真实验证范围；不保存机器偶然安装的版本、个人时区，不把一台机器的结果扩展成其他平台已验证。
