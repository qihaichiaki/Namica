## 被替代或收敛的方案

- **tooling 嵌套在 runtime 下：已被 D03 替代。** 独立顶层目录及构建目标是当前方向。
- **预先拆出 SystemPaths、AssetPaths、多层 Builder：已收敛。** 用户指出过细；当前建议按子系统提供集中入口，参见 ARCHITECTURE。
- **强制拆分 Base 宏头、改名数学 Utils、建立统一 serialization 子系统：不作为既定任务。** 这些是早期建议，近期讨论已允许保留更简单的组织。
- **编辑器保存场景直接等同正式发布流程：说明已补全。** 完整理解包含资源导入、内容准备、游戏代码、打包与运行；第一版实现可以简化。
- **根目录保留 AGENTS.md 或极简入口：已被 D08 替代。** 完整指引位于 `.agent/AGENTS.md`，后续由用户主动指定阅读。
- **本轮将 NAMICA_TOL 移入 math/Constants.h：已由 D10 明确延后。** 当前保留现状，未来归属与容差策略仍未定案。
- **通过 using 为未来内存池替换预留空间：已澄清适用边界。** 用户回顾了这一建议；2026-10-31 的讨论明确，别名只统一名称，接入内存池还需创建/释放策略与生命周期配合，不能承诺只改别名即可无缝替换。

## 当前建议，尚未获得逐项实施确认

- Runtime 以 core、app、math、io、platform、input、asset、render、scene 为参考子系统。
- FileSystem 可保留常用路径查询；图片职责可集中到 Image；未来 AssetManager 管理资源路径与加载。
- Tooling 初期使用 Project、AssetDatabase、AssetImporter、GameBuilder 等少量入口；可先做静态库。
- 第一款游戏逻辑可静态链接到编辑器和独立游戏，稍后再考虑动态模块。
- 使用稳定资源 ID、版本化数据、编辑/试玩状态隔离等长期约定。
- 首轮可先整理 Base/Common/Engine 的归属，再提取已有窗口和渲染实验能力。

这些内容是讨论基础，不是让 agent 自动创建目录、移动文件或实现框架的授权。
